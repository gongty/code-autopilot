# 设计线：总控怎么和 Claude Design 协作，怎么让开发照稿做

只有 Claude Code 有这个模式。设计线是一条普通的线（独立会话），在里面用 `Artifact` 工具从 Design 类型新建一张画布出稿，这就是 Claude Design。账号里要有 Design 类型，用 `Artifact` 列一下类型就能看到。

做法来自一个真项目：总控写好给 Claude Design 的总纲和分批任务，设计在同一个对话里一批批出稿，存进仓库的 `design/`，研发照这个目录做界面。

## 先知道 Claude Design 的几条规矩（读 Design 类型的说明得来，2026-11-16）

- **画板不是普通网页**：每张画板是一个 `.dc.html` 文件，要配 Claude Design 的运行环境才能打开。所以给研发的东西要另外整理进 `design/`（见下面「设计线交什么」）。
- **用户没要求，它不渲染、不截图、不回读自己的稿子来核。** 所以设计线的自检靠对着总纲逐条核；看样子的是用户；对稿（开发做出来的和稿子比）由总控另派子 agent 做，不靠设计线回读画布。
- **账号里有默认的设计系统（Design System），它会自动用上。** 不想用，总纲里写明「不用」。
- 画布的工作文件放在临时目录，它不会自己提交；进仓库的 `design/` 由设计线另外写。

## 什么时候开

- 新项目、有界面的大功能：开工第一批就开，和骨架线同时跑。
- 等设计的只有界面线；数据、接口、后台的线照常开。
- 设计没到的屏，界面线用最朴素的样子顶着，不自己发明视觉。

## 总控的活：把需求写清

照 `templates/design-brief.md` 写 `.code-autopilot/design/brief.md`：

- **总纲**：产品是什么、给谁用、什么气质；一定要有的和「不要出现」的；平台和尺寸（手机还是桌面、要不要深色模式）；用不用账号的设计系统；交付物。
- **分批**：每批几屏，按开发的顺序排：先出界面线最先要做的那几屏。每屏写清放什么内容、有哪些状态（空的、加载中、失败、内容很多）、从哪进来、点了去哪。
- **我替你定的**：需求里没定、出稿又必须有答案的，总控先定，写「定成什么、为什么」，用户不同意再改。
- **你定的**：用户在稿子上定下的，记原话和日期，后面每一批照着做。

## 三种交法（跟着模式走，记进项目卡）

全自动默认「直接出」，加强控制默认「每批都看」；加强控制的用户也可以选「先挑方向」。

| | 直接出 | 先挑方向 | 每批都看 |
| --- | --- | --- | --- |
| 视觉方向 | 设计线照总纲直接定一个，写下理由 | 出两三个方向，用户挑 | 同左 |
| 每一批 | 自检过了直接做下一批 | 第一批用户看过，之后自己一批接一批做完 | 每批用户看过才做下一批 |
| 设计线停下找人 | 要推翻总纲时找总控 | 要改定下来的方向、或要求互相矛盾时找用户 | 每批交了都等 |
| 那一批什么时候算定稿 | 总控验收过 | 方向定了、总控验收过 | 用户看过 |

- 定稿的那一批，总控合进主分支，界面线才开工做那几屏。
- 等用户看稿时，在 `notes.md` 记「等用户看设计」。巡检不算设计线卡住，只告诉用户稿子在哪。
- 用户可以点进设计线的会话直接说，也可以在画布上留言。

## 设计线交什么

1. **画布链接**：给用户看、留言。
2. **仓库里的 `design/`**，研发照这个做：
   - `design/tokens.css`：设计规范写成 CSS 变量（颜色、字号、间距、圆角、阴影，深浅两套的话两套都写）。这是唯一的一份，界面代码直接引用它。
   - `design/index.md`：每屏一行（表头见下）；再列组件清单，组件名就是界面代码里要用的名字。
   - `design/canvas/`：画板源文件（`.dc.html`）的副本，界面线和对稿的子 agent 照着读里面的结构和样式。

`design/index.md` 的表：

| 屏 | 批 | 画板 | 状态 | 从哪来、去哪 | 代码在哪 | 对过稿 |
| --- | --- | --- | --- | --- | --- | --- |
| 首页 | 1 | `canvas/Home.dc.html` | 空的、加载中、失败、内容很多 | 启动 → 首页 → 详情 | `src/pages/Home.tsx` | 11-16 对过 |

前五列设计线写，后两列总控写（界面线交了、对过稿时更新）。一眼就能看出哪屏设计到了、哪屏做了、哪屏对过。

## 开设计线怎么说

```
你是设计线，是线：不用 code-autopilot，不开新会话。先读 <主目录>/.code-autopilot/briefs/common.md（线的规矩）和 <主目录>/.code-autopilot/design/brief.md。
用 Artifact 工具从 Design 类型新建一张画布出稿（Claude Design），照它自己的规矩做。交法：<直接出 / 先挑方向 / 每批都看>。
同一个会话、同一张画布里一批接一批做：换了会话，定下的规范和组件就得重新交代。
每做完一批：
1. 照 brief 末尾「出稿后怎么看」里设计线自己核的那几条逐条核，有问题先改。
2. 更新仓库的 design/：tokens.css、index.md（前五列）、canvas/ 下的画板副本。只提交 design/ 下自己的文件，推自己的分支。
3. 报告写进 <主目录>/.code-autopilot/reports/<线名>.md：做到第几批、画布链接、补了哪些文案、哪些状态没做；会话里只回一两句和这个路径。
4. 停下等总控，不要归档：下一批、改稿都会发给你。
只在交法写的那几种情况停下找人，别的自己定，定了什么写进报告。
```

模型用最强档（型号见 `models.md`），思考强度高。

## 总控验收

- 对着 brief 看 `design/index.md`：该有的屏和状态齐不齐，「不要出现」的有没有出现。
- `tokens.css` 能不能直接给界面线用。
- 看样子交给用户（「先挑方向」「每批都看」）；「直接出」的，把链接附在给用户的里程碑消息里。
- 定稿了：把设计线的分支照常合进主分支，再派这一批的界面线。

## 衔接：让开发照稿做

最怕的是设计归设计、开发归开发，最后两个样。总控管住这几样：

1. **只有一份规范**：界面代码直接引用 `design/tokens.css` 的变量（或项目的样式系统从它生成），不把颜色、字号的数值抄进代码。组件名和 `index.md` 的组件清单一致。
2. **只做定稿的**：界面线只做已定稿、已合进主分支的那批屏。任务书写上画布链接、`design/index.md` 里对应的屏和批次、`design/canvas/` 里那几张画板的路径。
3. **交活附截图**：界面线交付时，用项目里的截图办法（Playwright 之类）把做的每屏、每个状态截下来，放 `.code-autopilot/shots/<线名>/`，路径写进报告。
4. **对稿**：总控派一个子 agent（不是界面线，中档，中），给它截图路径、那几张画板副本、`tokens.css` 和下面这段话。列出来的不一样，按第七节「发回要收敛」一次全发回界面线；拿不准是稿子没画到还是开发做错了，问设计线。对过稿才合，合完总控在 `index.md` 填「代码在哪」「对过稿」。
5. **改稿走总控**：设计要改，由总控发给设计线改（同一张画布里出新一版，旧版留着对比），`design/` 跟着更新、合进主分支，再通知用到那几屏的界面线。界面线不自己改视觉，设计线不改代码。

对稿子 agent 的话：

```
你是对稿的，只读。对比开发做出来的界面和设计稿，列出不一样的地方，10 分钟内交。
- 截图：<.code-autopilot/shots/<线名>/ 下的哪几张>
- 稿子：design/canvas/<哪几张>.dc.html（画板源文件，读里面的结构和样式）、design/tokens.css、design/index.md 里这几屏的行
逐屏、逐个状态比：布局和层级、用到的组件、颜色字号间距是不是 tokens.css 里的变量、文案、状态齐不齐。
每条写：哪屏哪个状态、稿上是什么、做出来是什么、截图文件名。看不清、稿上没画到的写「拿不准」，不硬说错。不提审美意见，只对稿。
```

## 没有 Claude Code 的时候

Codex、WorkBuddy 开不了设计线。总控照样写 brief，请用户拿到 Claude 里出稿，再照上面「设计线交什么」整理进 `design/`；衔接和对稿照上面做，对稿的子 agent 用当前环境的。
