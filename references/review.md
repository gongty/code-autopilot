# 验收和合并：细则

## 审查分三档

| 档 | 例子 | 审查 |
| --- | --- | --- |
| 照单执行 | 测试搭法、文档、一份共用名单、只改测试跟上新机制 | 不单独审，总控看一眼改动 |
| 改了一般行为 | 一个功能模块、一个页面、一条不碰核心的流程 | 一次子 agent 审查（中档，中） |
| 碰核心、真实数据、表结构、安全 | 核心模块、状态和生命周期、对外的规则、迁移、导数据、和安全有关的流程 | 认真审（最强档，中），必要时让同一个审查员复审 |

改界面的，另走一次对稿（`design.md`「衔接」）。

## 给审查员的话

三样必须写死：审哪段改动、跑哪几个测试、多久交。没写死，审查员就会通读仓库、改一点就跑整套，又慢又费额度。

- 你是审查员，不是作者。不改线的代码、不提交。要跑反例，在临时工作副本里跑：`git worktree add --detach <临时目录> <提交号>`，用完 `git worktree remove <临时目录>`；不在主目录里切分支、写文件。
- 审什么：分支 `<分支>`，base `<提交号>`，head `<提交号>`。先 `git diff <base>...<head> --stat`，重点看 `<几个文件>`。只看这段 diff 和它直接调用、被调用的地方，不通读仓库，不审没改的模块。
- 跑什么测试：只跑 `<和改动相关的测试文件>`，要验证反例就单独跑那一个。不跑整套，整套由总控合流过门时跑。
- 它该守的约定：`<任务书和方案里的几条>`。对着约定找确定的错，不对着风格。
- 每个改到的边界，写一句它该守的约定，再找最小的合法输入去推翻它。能跑的反例在 base 和 head 上各跑一次，base 过、head 挂才算退化。
- 按约定列全入口，逐条核对（正常做完、失败、叫停、超时、重启续上……），不是找到一个反例就交。
- 一个根子算一条：触发条件、哪个判断错了、结果错在哪、源码行。修法是补丁的（加特判、加兜底把问题盖住），也算一条。查不到证据的写「没覆盖到」，不硬说有错。
- 时限：小改动 5 分钟，大改动或碰真实数据 15 分钟。先查会拦合并的，到点用已有的写。
- 额度紧：大文件用 grep、sed 定位着读。

复审：续问同一个审查员（子 agent 做完还能用 `SendMessage` 续问），只看上次审过的 head 到新 head 的差分，加上次没结的那几条。只有接口、归属、共享的规则变了，才从头审。

## 发回要收敛

起因（2026-11-15）：一处「重启后接着做」审了四轮，每轮都抓到一条新漏的路，因为同一个事实由四处各算各写。第四轮总控不再让作者补第五处，改成「一条规则、一处计算」。

- 发回的是一类，不是一个反例。发回前先读代码，回答「为什么会漏」：几处各算一份、没有单一出口、状态没分清。发回里写结构上的改法，再要求按「每条路一行」的表把测试补全。
- 同一块第二次审出确定的错，按结构发回；第三次还漏，停止补，总控自己重新设计那一块（约定、单一出口、入口表），写成新任务书再派。
- 一次审查的确定问题一次全发回，不一条条发；发一条修一条再审，轮数会翻倍。
- **什么立刻修**：会拦合并的确定错，行为错、编译或测试挂、碰真实数据和安全的。
- **什么攒着一起修**：小问题；同一块、同一条规则上的几处（分开修，容易这次修好那次又坏）；要等别的线合进来才看得清的。记进 `plan.md` 的小问题清单，攒成一批一起修，修完只复审这一批的差分，不为它们单独再走一轮。

## 合流过门

先看项目卡的「合并方式」：

- **直接合**：照下面 1–6 步。
- **走 PR**：每条线交付时开 PR 到主分支。总控等 CI 过、守分支保护，不绕开必过的检查，不用管理员权限硬合。全自动的，总控自己合自己开的 PR；加强控制的，照项目卡写的由用户合，或用户点头后总控合。CI 挂了，照下面第 4、5 步判断是哪条线的、要不要发回。几条 PR 一起进时，一条合完，其余的先合主分支最新的再等 CI。
- **加强控制、又不走 PR**：照下面合到本地主分支、过了门以后，推送之前把改动摘要和 `git diff <合之前的提交号>..HEAD --stat` 发给用户，用户回「合」再推。

**门在哪跑**：在依赖装全的地方，和线交付前跑的是同一个环境、同一条命令（项目卡「门在哪跑」）。依赖没装全的地方跑出来的挂，不算数。

总控在主目录（签出主分支的那个文件夹）合。总控自己开在别的工作副本里的，命令都加 `git -C <主目录>`。

1. 先看能不能直接合：只交了一条，它已经把主分支最新的合进去、在自己工作副本里过了门，报告里写了过门时的 `git rev-parse HEAD^{tree}`。合完 `git rev-parse HEAD^{tree}` 和它一样，就不再跑门，直接推送。
2. 几条差不多同时交：一起合，跑一次门。合之前在主目录 `git status` 看干不干净：有不是你的、没提交的改动（比如用户正在改），先别合，问用户。记下主分支现在的提交号（`git rev-parse HEAD`），再按顺序 `git merge --no-ff <分支>`，说明写一句人话。全部合完，跑一次项目卡里的门（排队，见下）。
3. 过了：推送。
4. 没过：看挂的测试属于哪条线；`git reset --keep <合之前记下的提交号>` 撤掉本地合并（别用 `origin/<主分支>`：主分支上还没推的提交会一起丢），发回那条线；其余的重新合流再过一次门。
5. 挂的测试只在和别的一起跑时超时、单独跑能过、这次合的分支都没碰到它：放过，推送，记进小问题清单（写明哪个测试），不重跑门。
6. 有冲突：简单的总控解决；要判断的发回那条线。

## 门太慢怎么办

门本该几分钟。慢的那几次，都不是测试多：2026-11-16 03:49 和 04:29，同样三个测试文件 CPU 满着原地转了 17、19 分钟；08:28 三个测试文件跑完不退出，把门卡了 23 分钟，总控手动停掉才报出结果。几个门同时跑抢机器，还会跑出假的超时，线去修根本不存在的错。

按省时间多少排：

1. **门只跑受影响的测试**：检查（类型、lint、项目规矩）+ 改动牵连到的测试文件。挑法用测试工具自带的（vitest `--changed <base>`、`vitest related <文件>`，jest `--changedSince=<base>`，pytest 的 `pytest-testmon`），或照 import 关系自己写一张映射。写明什么时候跑整套：改了依赖或锁文件、改了测试配置、切换前。作者用过的一个门：检查 + 按 import 关系挑测试，平时 4 分钟左右，改了锁文件才跑整套（5–10 分钟）。
2. **每个测试文件有硬上限**：门的脚本给每个文件（或每一批）设上限，到点杀掉、记成挂、接着跑别的，最后列出超时的文件。跑完不退出的，多半是没关的定时器、连接、子进程：从测试里关掉，从根上修，不靠强制退出的开关盖住。
3. **线和合流用同一个门**：线交付前在自己工作副本跑的就是项目卡里那条门的命令、同一个 base，不是自己挑几个文件。挑法不一样，就会线上过了、合流才挂，多走一轮。
4. **门要排队**：同一时间只跑一个门，线和总控都排。最好写进门的脚本里（骨架线搭门时就写上）；现成的项目没有，就这样包一下：
   ```bash
   lock=<主目录>/.code-autopilot/gate.lock
   until mkdir "$lock" 2>/dev/null; do sleep 30; done   # 拿到锁才跑
   echo "<谁> $(date +%H:%M)" > "$lock/owner"
   <门的命令>; s=$?
   rm -rf "$lock"; exit $s
   ```
   锁比门的上限还老、`owner` 写的那个门已经不在跑了，就是没收拾的锁，删掉。
5. **过了门的不重跑**：见「合流过门」第 1 步。线交付前先把主分支最新的合进来再过门，总控合出来的代码就和它过门的那份一样，不用再跑。
6. **门里能并行的并行**：测试文件按 CPU 核数并行跑；类型检查、lint 开增量缓存（比如 tsc `--incremental`、eslint `--cache`）。开之前量一次、开之后量一次，确实快了才留。
7. **慢测试从根上改**：门跑完列出最慢的 10 个文件；sleep 和真实计时器换成假时钟，真实网络换成本地的假服务。改之前量一次、改之后量一次，不反复量。

## 合完

- 项目卡写了预览的，推送后马上重启，确认打得开。
- 清理工作副本和已合并的分支，只清不再派活的线的。还要接着派活的线留着它的工作副本，下一件先把主分支最新的合进来。
- 改计划里的进度；告诉用户一两句：合了什么、还有什么没验证。
- 有等这次合并的线，现在派。
- 跟用户说「这一版可以用了」之前，自己把主要路径走一遍，只查机械的：打得开、走得通、东西没丢。口气、手感、视觉这类项目卡写了用户自己验的，上预览交给用户试，总控不反复自测：总控对「好不好」的判断可能是偏的，自己反复试会把偏的当成对的，还费时间。

## 删分支、删工作副本之前

先看目标，三样都看清再删：

- **最后一次提交在什么时候**：`git log -1 --format='%h %cr %an' <分支>`。最近还有提交的，多半有人在用。
- **有没有别的会话占着或锁着**：`git worktree list` 看有没有 `locked`；会话列表里有没有一条线开在这个工作副本上；有没有进程开在这个目录里（`patrol.md` 的进程表）。
- **是谁的**：是这次开的线的，还是用户自己、别的会话开的。不是你开的，不删，写进报告问用户。

只删：已合进主分支、没有未提交改动、没人在用、不再派活的。删不了的，在阶段结束的清单里写明为什么留着。

## 改真实数据

迁移、导数据、批量改表，都走这个顺序，一步不跳：

1. **先在拷贝上跑**：拷一份真实数据，在拷贝上跑一遍迁移。
2. **逐表核对**：每张表前后的行数，加几条抽样记录，对得上才往下。
3. **整库备份**：真实数据整份备份，记下备份在哪、怎么恢复。
4. **停服务**：停掉会写这份数据的服务，免得迁移时有新写入。
5. **上线**：在真实数据上跑。
6. **再核一遍**：和第 2 步一样逐表核对；对不上就从备份恢复。

删真实数据还要用户点头，两种模式都一样。清旧的（旧代码、旧表、旧分支、旧文档）也一样：先列单子给用户，同意了再删。
