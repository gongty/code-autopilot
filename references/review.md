# 验收和合并：细则

## 审查分三档

| 档 | 例子 | 审查 |
| --- | --- | --- |
| 照单执行 | 测试搭法、文档、一份共用名单、只改测试跟上新机制 | 不单独审，总控看一眼改动 |
| 改核心行为 | 核心模块、状态和生命周期、对外的规则 | 一次子 agent 审查 |
| 碰真实数据、表结构、安全 | 迁移、导数据、和安全有关的流程 | 认真审，必要时让同一个审查员复审 |

## 给审查员的话

- 你是审查员，不是作者。只读，不改文件不提交。
- 审什么：分支 `<分支>`，base `<提交号>`，head `<提交号>`。先 `git diff <base>...<head> --stat`，重点看 `<几个文件>`。
- 它该守的约定：`<任务书和方案里的几条>`。对着约定找确定的错，不对着风格。
- 每个改到的边界，写一句它该守的约定，再找最小的合法输入去推翻它。能跑的反例在 base 和 head 上各跑一次，base 过、head 挂才算退化。
- 按约定列全入口，逐条核对（正常做完、失败、叫停、超时、重启续上……），不是找到一个反例就交。
- 一个根子算一条：触发条件、哪个判断错了、结果错在哪、源码行。查不到证据的写「没覆盖到」，不硬说有错。
- 时限：小改动 5 分钟，大改动或碰真实数据 15 分钟。先查会拦合并的，到点用已有的写。
- 额度紧：大文件用 grep、sed 定位着读。

复审：续用同一个审查员，只看上次审过的 head 到新 head 的差分，加上次没结的那几条。只有接口、归属、共享的规则变了，才从头审。

## 发回要收敛

起因（2026-11-15）：一处「重启后接着做」审了四轮，每轮都抓到一条新漏的路，因为同一个事实由四处各算各写。第四轮总控不再让作者补第五处，改成「一条规则、一处计算」。

- 发回的是一类，不是一个反例。发回前先读代码，回答「为什么会漏」：几处各算一份、没有单一出口、状态没分清。发回里写结构上的改法，再要求按「每条路一行」的表把测试补全。
- 同一块第二次审出确定的错，按结构发回；第三次还漏，停止补，总控自己重新设计那一块（约定、单一出口、入口表），写成新任务书再派。
- 小问题不为它们再走一轮，记进进度的清单，以后一起做。

## 合流过门

1. 验收过的分支先不急着合，攒两三条（或者一时没有别的线快做完）再一起。
2. 在主目录按顺序 `git merge --no-ff <分支>`，说明写一句人话。全部合到本地主分支后，跑一次项目卡里的门。同一时间只跑一个门，几个门抢机器会跑出假的超时。
3. 过了：推送。
4. 没过：看挂的测试属于哪条线；`git reset --keep origin/<主分支>` 撤掉本地合并，发回那条线；其余的重新合流再过一次门。
5. 挂的测试这次合的分支都没碰到，单独跑又过：推送，记进小问题清单，不重跑门。
6. 有冲突：简单的总控解决；要判断的发回那条线。

## 合完

- 项目卡写了预览的，推送后马上重启，确认打得开。
- 清理做完的工作副本和已合并的分支（只删已合进主分支、没有未提交改动、没人在用的）。
- 改进度文件；告诉用户一两句：合了什么、还有什么没验证。
- 有等这次合并的线，现在派。
- 跟用户说「这一版可以用了」之前，自己把整个产品走一遍。
