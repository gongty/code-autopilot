# 项目梳理提示词

照代码证据把项目理一遍，找出最值得解决的结构问题，防止项目越改越乱、变成屎山。只读，不改东西。比直接说「帮我看看项目有什么问题」效果好得多。

**什么时候用**：要重构、但根因拿不准（总控自己开）；或者用户觉得项目乱了、改一处坏一处（用户要了就跑）。

**怎么跑**：开一条只读的线，最强档，思考强度高（型号见 `references/models.md`）。不改代码，所以可以不要工作副本，在主目录读就行。把下面分隔线以下的整段原样发给它，交回的报告由总控读，拿来定重构的范围和开发计划。

---

请对当前项目做一次基于代码证据的项目梳理，找出最值得解决的结构问题，为后续开发和性能优化提供依据。本轮只读分析，不实施改造。

目标是：

1. 弄清已有功能如何实现、彼此如何协作。
2. 找出重复维护、隐藏依赖和职责混乱的根因。
3. 降低后续 AI 开发的定位、理解、修改和验证成本。
4. 找出可能影响运行效率的问题，明确哪些已有证据、哪些需要测量。

不以减少代码行数、拆分文件数量、增加文档数量或提高工具评分作为成功标准。

## 一、先确认项目事实

遵守项目的 AGENTS.md（或 CLAUDE.md）。先读项目已有的产品定义、代码结构、产品结构、进度、验收总表、经验记录（有哪些读哪些），以及分析涉及的专项文档；检查 git 状态、当前分支和近期提交，辨认正在进行的工作。

区分三类信息：

- 用户已经确定的产品要求和约束；
- 当前代码实际实现的行为；
- 文档描述与尚未验证的判断。

代码与文档不一致时，指出具体差异；不要擅自把实现偏差当作新的产品决定，也不要重新讨论用户已经确定的要求。

本轮不修改代码、文档、配置或依赖，不安装工具，不提交推送，不启停服务，不调用收费接口。真实用户数据只读且按需访问，不展示密钥或无关隐私。

## 二、建立功能到实现的地图

先建立全仓模块轮廓，再追踪主要功能的完整链路：

用户操作或系统事件 → 入口 → 核心判断与处理 → 数据存储或外部能力 → 状态变化 → 用户最终收到的结果 → 对应测试与观测记录。

项目里有 agent 能力的，区分工具登记、模型选择、实际执行、结果回传与最终使用结果，不能把「工具存在」当作「能力已经走通」。

每条链路标出关键文件、符号、模块边界，以及状态和规则的唯一来源。结合代码调用、配置注册、事件订阅和动态加载核对，不能只按目录名或文档推断。

优先复用现有文档的组织方式。本轮在报告中说明哪些现有文档应补充或纠正，不另建一套重复资料。

## 三、围绕修改成本检查结构

重点检查：

- 同一业务规则、状态或数据是否有多份实现，是否需要同步修改。
- 应该一起变化的代码是否被分散，不该一起变化的职责是否被绑定。
- 模块是否依赖其他模块的内部细节、隐含顺序、全局状态或未声明约定。
- 是否存在循环依赖、错误的依赖方向或跨层读写。
- 是否存在没有独立职责的包装、用不上的扩展点、重复执行路径、过期兼容实现。
- 局部特判是否反映了更深层的模型、边界或数据来源问题。
- 测试和观测是否足以发现这些链路的真实失败。

判断重复时，确认它们是否承担同一业务责任；不能因为代码长得像就合并。

判断无用时，核对程序入口、脚本、配置、动态调用、对外接口与兼容责任；「搜索不到引用」只能作为线索。

判断抽象是否合理时，解释它保护了什么边界、减少了什么重复，以及付出了什么理解成本。不要机械地合并、拆分或引入设计模式。

## 四、单独判断运行效率

沿真实执行路径检查串行等待、重复计算、重复读写、数据库访问、外部请求、资源生命周期、前端加载和渲染。

优先使用已有计时、日志、构建信息和性能证据。

明确区分：

- 已测得的瓶颈；
- 代码能够证明的额外工作；
- 尚需测量的性能假设。

没有测量就不承诺速度、内存或成本改善。对假设说明最小验证方式，以及什么结果会推翻判断。

## 五、从根因提出改造建议

每个有效问题都给出：

- 现象与代码证据：真实路径、关键符号，必要时附行号。
- 根因：为什么当前结构会产生这个问题。
- 实际影响：影响什么功能、增加什么修改成本或运行开销。
- 根本改法：改变哪个责任、依赖、状态来源或执行过程。
- 行为约束：必须保留哪些既有功能和产品要求。
- 改动范围、风险和最小有效验证方法。
- 结论的确定程度与仍待核实之处。

优先寻找能同时消除多个问题的共同根因。不要用增加过滤、拦截、局部特判或层层兜底掩盖结构问题。

证据不足的标为待核实；现有结构合理的明确保留。不要为了交付一份问题清单而凑问题。

## 六、最终交付

请在当前对话中给出：

1. 总体结论：当前项目最影响后续开发的是什么，依据是什么。
2. 功能与实现地图：用紧凑表格呈现主要链路和代码位置。
3. 问题清单：合并同一根因，按实际影响、证据确定性和改动风险排序。
4. 分阶段建议：说明最值得先做的一阶段，为什么先做、涉及哪里、如何验收，以及哪些工作应等证据充分后再做。
5. 覆盖边界：实际读过、追踪过和验证过什么，哪些没有覆盖。

全仓轮廓与重点链路深查分开说明，不能把抽样检查写成全项目已经验证。

执行过程中自行完成必要的只读调查，不要只返回计划或中途停下让我选择分析方向。遇到无法确认的事实，记录不确定性并继续其他分析。最终建议必须让我看得清楚：为什么值得改、究竟改哪里，以及怎样证明改完更好。
